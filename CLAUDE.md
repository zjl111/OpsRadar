# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

OpsRadar is a production inspection platform: FastAPI + PostgreSQL + Redis + Celery backend that runs real Linux/Unix host inspections over SSH, plus a task-oriented AI assistant that orchestrates inspection workflows. PostgreSQL is the only supported database (SQLite is explicitly rejected at startup).

## Commands

All backend code runs as a module from the repo root (the package is `backend.app`, not a top-level `app`).

```bash
# Lifecycle (also exposed via scripts/run_*.sh which set dev env vars first)
python3 -m backend.app.cli migrate        # alembic upgrade head — schema is ONLY created this way
python3 -m backend.app.cli seed-builtin    # built-in roles, inspection items, rule sets
python3 -m backend.app.cli init-admin      # seeds builtin + creates admin user
python3 -m backend.app.cli check           # verify Postgres/Redis reachability

# Run locally (Postgres + Redis must be up first)
bash scripts/run_dev.sh       # uvicorn --reload on :4173 (runs migrate + seed first)
bash scripts/run_worker.sh    # celery worker
python3 -m backend.app.beat   # cron scanner (polls CronPlan every OPSRADAR_BEAT_INTERVAL_SECONDS)
```

### Verification (this is the test suite — there is no pytest)

```bash
python3 scripts/check_services.py          # Postgres + Redis connectivity
python3 -m compileall backend              # syntax-check all backend code
node --check assets/app.js                 # syntax-check the frontend bundle
python3 scripts/smoke_test.py http://127.0.0.1:4173   # login + /bootstrap end-to-end; prints "smoke ok"
```

Run `compileall` after backend edits and `node --check assets/app.js` after frontend edits. The smoke test requires a running API, worker, Postgres, and Redis, and logs in as `admin / OpsRadar@123`.

## Architecture

Three processes share one codebase and one database:

- **API** (`backend/app/main.py` → `backend/app/api/routes.py`): FastAPI. `routes.py` is a single ~3200-line module holding every endpoint plus its payload-serialization helpers. It also serves the frontend (`/` → `backend/app/static/index.html`, SPA fallback for unknown paths, `/assets` static mount).
- **Worker** (`backend/app/worker/celery_app.py`): one Celery task, `run_inspection_task`, which calls `inspection_engine.run_task`. On `worker_ready` it runs `recover_stale_tasks` to fail tasks stuck in `running` past `OPSRADAR_MAX_TASK_SECONDS`.
- **Beat** (`backend/app/beat.py`): a plain polling loop (not Celery beat) that finds due `CronPlan` rows, creates tasks via `create_manual_task`, and enqueues them.

### Request flow for an inspection

`create_manual_task` (in `inspection_engine.py`) snapshots each resource+item into `TaskResult` rows at creation time — execution later reads the snapshot, not live config (except credentials, which are re-read fresh). The API/beat sets the task `queued` and calls `run_inspection_task.delay(task_id)`. The worker runs `run_task`, which iterates `TaskResult` rows through `InspectionExecutor`, and on each `fail`/`exception` creates an `Issue` plus a diagnosis record (`AiAnalysisJob` + `AiAnalysisResult` seeded from `diagnose_tools` + `analysis.build_issue_insight`). When finished it calls `persist_inspection_report` and back-links the issues to the report.

### Executors (`services/executors.py`)

`InspectionExecutor.execute` dispatches on `(resource.type, item.command_type)`. Shell-over-SSH (host/linux/server/container/compose/systemd) is the primary path; Postgres/MySQL/Redis executors also exist. `_compatible` in `inspection_engine.py` gates which items attach to which resources at task-creation time. All command output passes through `masking.mask_sensitive` before being stored.

### AI assistant is a persisted state machine, not a chatbot

`services/ai_actions.py` is the orchestrator. A user message creates an `AiWorkflow` row; `_advance_workflow` computes the current `state` and the `next_actions` (UI buttons) from real platform data, persisting both. When the user completes a modal the frontend posts a callback event (`environment_created`, `asset_created`, `connection_tested`, `rules_confirmed`, `task_created`, etc.) which `handle_workflow_event` applies before re-advancing. Key invariants when editing this file:

- Every action is declared in `ACTION_SPECS` / `WORKFLOW_ACTIONS` with an RBAC `permission` and a `mutating` flag. Mutating actions must `requires_confirmation` in their UI action.
- The assistant must never fabricate assets, results, reports, or issues — all returned data comes from executed actions against the DB.

### Data model (`models/entities.py`)

All models live in one file. IDs are prefixed strings generated by `new_id("usr")`, `new_id("tsk")`, etc. (not integers). Core chain: `Application` → `AppEnvironment` → `EnvironmentResource` → `Resource`; inspections produce `Task` → `TaskResult` → `Issue` → `RepairTask`, with `InspectionReport` and `IssueInsight` derived. `RuleSet` + `InspectionItem` define what gets checked; `EnvironmentRuleSet` binds rule sets to environments.

### Schema management — important

The app **never calls `create_all`**. Schema exists only after running Alembic migrations (`migrations/versions/`), and built-in data only after `seed-builtin`. When you add or change a model in `entities.py`, you must add a matching migration in `migrations/versions/` (numbered `YYYYMMDD_NNNN_name.py`) — the running app will not auto-create the table.

## Security model

- **Auth**: JWT bearer tokens. `require_user` (FastAPI dependency) validates the token; `require_permission(db, user, "area:action")` enforces RBAC. Missing token → 401, missing permission → 403.
- **RBAC**: permissions are strings on `Role.permissions` (JSON). `has_permission` honors `*` (all) and `area:*` wildcards. The full catalog is `ALL_PERMISSIONS` in `services/rbac.py`.
- **Credentials**: resource secrets are AES-256-GCM encrypted (`services/crypto.py`) into `Resource.extra_params["credential_encrypted"]`, decrypted only in-worker at execution time. The key derives from `OPSRADAR_ENCRYPTION_KEY` (required in production — startup raises if it's still a placeholder). API responses never return credentials, and `_record_issue_diagnosis`/snapshots exclude them. Legacy plaintext credentials are rejected, not migrated.
- Write and security-relevant events are recorded as `AuditLog` rows.

## Frontend

Vanilla-JS single-page app with **no build step and no package.json**: `assets/app.js` (one large bundle), `assets/styles.css`, loaded by `backend/app/static/index.html`. Edit the files directly and verify with `node --check assets/app.js`. The frontend only renders state and `next_actions` the API returns — workflow logic stays on the backend.

## Config

Everything is `OPSRADAR_*` env vars read in `backend/app/core/config.py` into a frozen `Settings`. `OPSRADAR_ENV=production` triggers strict checks (encryption key, secret key must not be placeholders). See `.env.example` and the README's Configuration section for the full list.
